# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a [CONTAINERlab](https://containerlab.dev/) network lab of [FRRouting (FRR)](https://frrouting.org/) nodes demonstrating Segment Routing IPv6 (SRv6) — specifically SRv6 uSID as the transport for IPv4/IPv6 BGP L3VPN services. It is a config/infra repo, not an application: the "source code" is FRR configuration files, container init shell scripts, and a CONTAINERlab topology definition. See `images/topology.png` for the physical/logical topology.

## Lab lifecycle commands

There is no build/lint/test suite here — "testing" a change means redeploying the lab and inspecting control-plane/data-plane state via `vtysh`. `ROUTE-EXPORT-VALIDATION.md` documents the reference pattern for proving a route/service works end to end (VRF RIB → VRF BGP table → VPN table → advertisement → remote install with `seg6` forwarding info); follow that pattern when validating new services.

- `make lab` (or `sudo clab deploy -t lab.yml`) — deploy the topology; applies each node's `frr.conf` and runs its init script
- `make clean` (or `clab destroy -t lab.yml`) — tear down the lab
- `make inspect` — show running lab state
- `make pe1` / `pe2` / `p1` / `p2` / `p3` / `p4` / `rrv6` / `bdr1` — drop into `vtysh` on that router
- `make c1` / `c2` / `c3` — shell into a client container
- Direct access: `docker exec -it clab-frr-srv6-<node> vtysh` or `bash`
- Packet capture on the host: `sudo ip netns exec clab-frr-srv6-<node> tcpdump -nni <iface>`

CONTAINERlab requires sudo. `sudo clab deploy` requires no prior `make initialize-log` step — `make lab`/`make clean` handle that and log to `setup.log`.

## Repository structure

Each router has its own directory (`pe1/`, `pe2/`, `p1/`–`p4/`, `rrv6/`, `bdr1/`) containing a consistent 4-file set, all bind-mounted into the container by `lab.yml`:

- `frr.conf` — the FRR configuration (interfaces, IS-IS, BGP, SRv6 locator/segment-routing stanzas)
- `daemons` — which FRR daemons run (`bgpd`+`isisd` only; everything else disabled)
- `vtysh.conf`
- `<node>.sh` — container init script run at deploy time (sysctl `net.ipv6.conf.all.forwarding`/`seg6_enabled`, creates the dummy `sr0` SRv6 interface, and on PEs, wires up VLAN subinterfaces + Linux VRF devices for the RED/BLUE services)

To change a router's behavior, edit its `frr.conf` and/or `.sh`, then redeploy. `lab.yml` is the single source of truth for topology — node roles, management IPs, and the interface link map (`p1:eth2` ↔ `p2:eth1`, etc.); `frr.conf` interface `description` lines mirror these links, so cross-reference `lab.yml` when tracing what a given `ethN` connects to.

Other directories:

- `clients/` — `client1.sh`/`client2.sh`/`client3.sh`, analogous init scripts for the `wbitt/network-multitool` client containers (c1→pe1, c2→pe2, c3→pe1), adding VLAN subinterfaces into the RED/BLUE VRFs
- `scripts/srv6_pseudo_controller.py` — standalone operator tool (not part of the deployed topology) that interactively provisions an additional ad hoc SRv6 L3VPN VRF service against an already-running lab, driving `pe1`/`pe2`/`c1`/`c2` live via `docker exec`/`vtysh`. Supports `--dry-run` to print commands without applying them.
- `grafana/`, `loki/`, `promtail/` — logging/observability stack config wired into `lab.yml`; once deployed, browse to `http://localhost:3000` (Grafana) → "Network Logs" dashboard
- `clab-frr-srv6/` — gitignored, generated by CONTAINERlab at deploy time (runtime state, TLS certs, inventories); not source
- `logs/` — per-node FRR logs, gitignored except `.gitkeep`

## Network design conventions

- IPv6 loopbacks: `2001:face::y/128` per node
- IPv6 point-to-point links: `2001:c0de:1:y::z/64`
- SRv6 locators: uSID `f3216` format (32-bit block + 16-bit node ID), `fcdd:dd00:01xx::/48` per node, locator name `MAIN`. Only Flex-Algo 0 is implemented — FRR 10.7.0 doesn't yet support multiple SRv6 locators or Flex-Algo, though the locator schema reserves bits for future expansion (see README for the bit breakdown)
- BGP/IS-IS router IDs: `172.16.0.y/32` (unrouted, ID-only)
- IS-IS: single Level-2 area, NET `49.0001.xxxx.xxxx.xxxx.00` derived from the router ID
- BGP: ASN 65000, PEs (`pe1`, `pe2`, `bdr1`) peer with route reflector `rrv6`. L3VPN uses the per-VRF SID model (`sid vpn per-vrf export auto`, one SID per VRF covering both address families) rather than per-AF. RED VRF = RT `65000:10`, BLUE VRF = RT `65000:20`

**Known limitation**: the global/default-table SRv6 scaffold between `pe1` and `bdr1` (simulating Internet routes, `10.11.1.0/30` / `99.99.99.99/32`) does not work end-to-end in the current FRR version. SID allocation and control-plane advertisement work, but the local SRv6 service (post-decap lookup) fails to install in the default table/VRF 0 — likely because FRR's SRv6 local-service install path expects a Linux VRF device, which the default table lacks. Treat that part of the lab as a control-plane/SID-allocation demo only; RED/BLUE VRF service SRv6 forwarding is fully working. See the "Global Table SRv6 Note" section of README.md for details.
